1. ملخص تنفيذي وحالة الجاهزية

6.0/10
مؤشر الجاهزية للإنتاج. الهندسةُ الأمنيةُ والهيكليةُ أفضل بكثير من المتوسط في هذا النوع من المشاريع (لا RCE، لا SQL injection، لا تسريب مفاتيح، ACID حقيقي، 254 اختبارًا ناجحًا، lint/typecheck نظيفان). لكن النظام لا يؤدي وظيفته من الطرف إلى الطرف اليوم: مسار السحب (pull) يفشل بنسبة 100% ضد العامل المنشور، ومرآة التقارير معطّلة كليًا على هذا الجهاز. الخلل ليس في التصميم بل في "التوصيل" (wiring) بين الأجزاء.

نقاط القوة المعمارية (مُتحقَّق منها)

  • Electron hardening مكتمل: sandbox:true، contextIsolation:true، nodeIntegration:false، لا remote، منع التنقل وفتح النوافذ — electron/main.cjs:43-82.
  • صفر SQL injection: كل استعلام في العُمّال مُهيَّأ بـ ? مرتبط، وكل مُعرّف جدول/عمود يأتي من خرائط ثابتة في الكود لا من المدخلات.
  • صفر تسريب أسرار في حزم البناء: تم البحث عن القيمة الحقيقية لـ VITE_CF_WORKER_API_KEY (19 محرفًا) في dist/ وreports-site/dist/ → صفر تطابق. بوابة التقارير تمرّ أيضًا بفحص "sentinel" إجباري أثناء البناء (scripts/build-reports.mjs:46-55).
  • ACID حقيقي: إنشاء الطلب يغلّف (إدراج الطلب + العدّاد اليومي + دفتر نقاط الولاء + خصم المخزون) في معاملة واحدة OrderRepository.cjs:108-159، مع WAL وbusy_timeout=5000.
  • التحقق عند كل قناة IPC: طبقة electron/validate.cjs تُطبَّق على كل ipcMain.handle، مع قائمة سماح للإعدادات ومفاتيح "write-only" لا تُقرأ أبدًا (main.cjs:191-224).
  • كلمة مرور الجهاز: PBKDF2-SHA256، 210,000 تكرار، ملح عشوائي لكل سجل (src/utils/password.ts:13)، ومقارنة ثابتة الزمن.
  • جودة الكود: eslint --max-warnings 0 نظيف، tsc --noEmit نظيف للجذر وللبوابة، 254 اختبارًا ناجحًا من 254.

أهم ما يمنع الإطلاق

  • حرج مرآة التقارير معطّلة صمتًا: لا يوجد VITE_REPORTS_API_KEY في .env.
  • حرج العامل المنشور يرفض كل طلبات السحب: 400 {"success":false,"error":"Missing sql or batch"}.
  • عالي دمجُ stock وpoints بنظام Last-Write-Wins → ضياع تحديثات وإنفاق مزدوج.
  • عالي مفتاح API واحد مشترك يمنح قراءة/كتابة كل الفروع.
  • عالي الحذف الناعم "طريق باتجاه واحد" في السحابة.
  • متوسط سجلات التطبيق بلا تدوير → نمو غير محدود على أجهزة الكاشير.

F3 عالي — دمج Last-Write-Wins على عدّادات قابلة للتغيير (stock، points)

الموقع: cloudflare/d1-proxy-worker.js:288-300 (inventory) و:265-275 (customers) — ويُعاد محليًا عبر syncEngine.cjs:194-199 ← InventoryRepository.upsertPulledInventory:64-100

التحليل: stock وpoints ليسا "حالة نهائية" بل مجموع تراكمي، لكنهما يُكتبان كقيمة مطلقة بقاعدة "الأحدث يفوز":

-- d1-proxy-worker.js:288-300 (inventory)
ON CONFLICT(id) DO UPDATE SET
  stock = excluded.stock,                 -- قيمة مطلقة، لا فرق!
  updated_at = excluded.updated_at
WHERE excluded.updated_at > inventory.updated_at OR inventory.updated_at IS NULL

-- d1-proxy-worker.js:265-275 (customers)
ON CONFLICT(id) DO UPDATE SET points = excluded.points, ...

دفتر الحركات (inventory_transactions) صحيح لأنه append-only بـ INSERT OR IGNORE (:334-335) — لكن لا أحد يقرأ منه لإعادة حساب الرصيد؛ reports-site/src/analytics.ts:184-203 يستخدمه للتكلفة فقط، بينما شاشة المخزون تقرأ inventory.stock مباشرة.

السيناريو الأسوأ (إنفاق مزدوج للولاء): رصيد العميل 100 نقطة. الفرع (أ) يستبدل 50 والفرع (ب) يستبدل 50 في نفس الدقيقة وكلاهما offline. كلٌّ يرسل points = 50. الأحدث يفوز → الرصيد 50، والعميل استردّ 100 نقطة من رصيد 100 مرتين في فاتورتين مختلفتين. نفس المنطق على المخزون: بيعتان متزامنتان لصنف مشترك (branch_id IS NULL) تُسجَّلان خصمًا واحدًا → inventory drift دائم لا يُكتشف.

الإصلاح — تحويل العدّادات إلى مشتقّة (derived) من دفتر الحركات

// BEFORE — d1-proxy-worker.js:288 : كتابة القيمة المطلقة
ON CONFLICT(id) DO UPDATE SET
  stock = excluded.stock,
  updated_at = excluded.updated_at
WHERE excluded.updated_at > inventory.updated_at OR inventory.updated_at IS NULL

// AFTER — لا تُزامَن القيمة المطلقة أبدًا؛ الرصيد يُشتق من الدفتر
ON CONFLICT(id) DO UPDATE SET
  name = excluded.name,
  unit = excluded.unit,
  minStock = excluded.minStock,
  costPerUnit = excluded.costPerUnit,
  branch_id = excluded.branch_id,
  updated_at = excluded.updated_at
  -- stock محذوف عمدًا: هو SUM(quantity) من inventory_transactions
WHERE excluded.updated_at > inventory.updated_at OR inventory.updated_at IS NULL

// AFTER — رصيد المخزون يُقرأ مشتقًا (worker، readManagerSnapshot):
SELECT i.*, COALESCE((
  SELECT SUM(CASE WHEN t.type = 'OUT' THEN -t.quantity ELSE t.quantity END)
  FROM inventory_transactions t WHERE t.itemId = i.id
), 0) AS computed_stock
FROM inventory i WHERE i.deleted_at IS NULL

// AFTER — رصيد النقاط يُشتق من points_transactions بدل عمود customers.points
SELECT c.*, COALESCE((
  SELECT SUM(p.points) FROM points_transactions p WHERE p.customerId = c.id
), 0) AS computed_points
FROM customers c WHERE c.deleted_at IS NULL

وبما أن inventory_transactions وpoints_transactions append-only ومفتاحها id (UUID)، فإعادة الإرسال آمنة تمامًا (idempotent) — وهذا يحقق شرط "لا خصم مزدوج" بصورة صحيحة بدل الاعتماد على ترتيب وصول الرسائل.
